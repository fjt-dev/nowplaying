## サービス終了について

本サービスでは、複数の音楽配信サービスへのリンクを取得するためにOdesli APIを使用していました。同APIの廃止に伴い、従来の構成でサービスを継続することが難しくなりました。

各音楽サービスのAPIや代替のリンク変換APIへの移行を検討しましたが、利用条件・継続費用・利用枠などの制約があり、個人開発として維持できる構成の確立には至りませんでした。

インフラエンジニアのポートフォリオとして再設計することも検討しましたが、その前提となる音楽データの取得手段の確保に多くの検討が必要となりました。今後取り組みたいインフラの設計・運用と、開発・維持にかかる負担を踏まえ、本プロジェクトを終了し、新たな作品に取り組むことにしました。

ご利用いただき、ありがとうございました。

## 制作背景

制作当時、Apple MusicのリンクをTwitterで共有してもプレビューが表示されず、曲の情報が伝わりにくいと感じていました。また、共有相手が別の音楽配信サービスを利用している場合、そのサービスで曲を探し直す必要がありました。

お気に入りの曲を紹介しても、サービスの違いによって聴いてもらいにくいというもどかしさが、開発のきっかけです。複数サービスへのリンクとOGPを備えた共有ページを用意することで、この手間を減らすことを目指しました。

UI設計ではNexTone Linkを参考にしました。背景にはアルバムアート自体をCSSでぼかして使用しています。

## 設計上の判断

### Route HandlerへのAPI呼び出しの集約

Odesli APIの呼び出しを`app/api/resolve/route.ts`に集約し、共有ページやOGPの生成処理から`/api/resolve`を通じて利用する構成にしました。

外部APIへのアクセス処理をまとめる一方、返却データにはOdesliの形式をそのまま使用していました。そのため、別のAPIへの移行には、呼び出し処理に加えて型定義や画面側のデータ参照も見直す必要がある設計でした。

### クエリパラメータを使った共有URL

共有ページのURLに入力元の音楽サービスのURLをクエリパラメータとして含め、DBを持たずに共有できる構成にしました。ブラウザ拡張機能などからURLを渡す使い方も想定していました。

### URLの正規化

SpotifyのURLに含まれる`/intl-ja`やクエリパラメータを取り除き、Apple Musicでは曲を識別する`i`パラメータを残して正規化しました。共有時に付加される情報を除き、APIに渡すURLの形式を揃えています。

## 検討した改善

サービスの継続とインフラ面の強化に向けて、以下の改善を検討しました。いずれも構想・調査段階のもので、実装には至っていません。

- **音楽APIの移行**  
  Spotify Web API・Apple Music API・YouTube Data APIの組み合わせや、代替のリンク変換APIを検討しました。各サービスの利用条件・費用・利用枠を踏まえ、対応範囲の見直しも検討しました。

- **検索・照合精度の改善**  
  ISRCや曲名・アーティスト名を用いた照合と、LLMによる候補の比較を検討しました。LLMについては、取得データのAI利用に関する制約もあり、採用には至りませんでした。

- **共有URLとデータ保存の見直し**  
  変換結果を保存し、共有IDで参照する方式を検討しました。外部APIに障害が発生しても、保存済みの情報から共有ページやOGPを表示できる構成を目指していました。

- **インフラと運用基盤の整備**  
  API処理の分離、キャッシュ、利用量制御、監視、CI/CD、Infrastructure as Codeの導入を検討しました。

- **利用方法と対応サービスの拡充**  
  ブラウザ拡張機能やAppleショートカットへの対応、音楽配信サービスの追加を構想していました。
